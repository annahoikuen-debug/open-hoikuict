# 実装計画 23: 未解決テスト失敗の修正（2026-11-19）

## 概要

実装計画 22（コードレビュー指摘修正）のリグレッションテスト実行時に判明した、
**コードレビュー修正とは無関係の事前存在テスト失敗 8 件**を修正する。

失敗原因は 3 グループに分類され、いずれも「機能追加/テンプレート変更に
テスト期待値が追従していない」ことが根本原因。production コードのバグではなく、
**テスト期待値の更新**または**テストのフィルタ条件追加**で対応する。

## 失敗一覧と原因分類

| グループ | テスト | 失敗内容 | 根本原因 |
|----------|--------|----------|----------|
| A | `test_settings_sessions.py::test_hub_respects_roles_and_opening_does_not_save[admin-11]` | `settings-item` 数 13 ≠ 期待値 11 | 設定ハブに新規項目追加（ヘルスチェック等）されたが期待値未更新 |
| A | 同 `[can_edit-2]` / `[view_only-2]` | 4 ≠ 2 | 同上（非管理職にも見える新項目） |
| A | `test_disabled_parent_registration_link_hidden` | 12 ≠ 10 | 同上 |
| B | `test_parent_notice_order.py::test_publication_date_and_local_survey_time_are_compared_in_same_timezone` | `/parent-portal/notices` に `unanswered-survey` が混入 | `/notices` 一覧が survey をフィルタせず全 updates を返すようになった |
| C | `test_parent_portal.py::test_staff_can_publish_daily_contact_reply_to_parent` | 詳細ページに「更新者: 台帳担当」が表示されない | 連絡帳承認フロー追加（Wave E P4-3）で更新者表示ロジックが変化 |

## Task A: 設定ハブの項目数期待値更新（優先度: 高・テストのみ）

### 現状

`templates/settings/index.html` には以下が実装済み（テスト作成後に追加された機能）:

- P1-1 設定ヘルスチェック診断バナー（admin のみ・`settings-item` ではないが
  項目数に影響するリンク/要素）→ 実際はバナーでカウント外。
- **定型文テンプレート管理** (`/message-templates`) — 全ロール表示（38 行目付近）→ 非管理職 +2 の原因
- admin セクションの項目増（職員管理・職員権限設定等）→ admin +2 の原因

実際のカウント（現行テンプレート）:

| ロール | 期待値（テスト） | 実測値 |
|--------|------------------|--------|
| admin | 11 | **13** |
| can_edit | 2 | **4** |
| view_only | 2 | **4** |
| parent-auth disabled（admin） | 10 | **12** |

差分はいずれも +2。

### 実装内容（テストのみ修正）

1. `tests/routers/test_settings_sessions.py` の `test_hub_respects_roles_and_opening_does_not_save`
   パラメータを現行テンプレートに合わせて更新:

```python
@pytest.mark.parametrize("role,count", [(Role.ADMIN, 13), (Role.CAN_EDIT, 4), (Role.VIEW_ONLY, 4)])
```

2. `test_disabled_parent_registration_link_hidden` の期待値も同様に 12 に更新:

```python
assert response.text.count('class="settings-item ') == 12
```

3. **確認事項（実装前チェック）**: `pytest -q "tests/routers/test_settings_sessions.py::test_hub_respects_roles_and_opening_does_not_save"` を
   実行し、各ロールの実測カウントを先に確認してから値を確定する。
   （テンプレートの権限分岐 `{% if current_user.is_admin %}` の影響で
   ロール別の実測値が変化する可能性があるため）

### 判断基準

- テンプレート側の項目追加は意図的な機能（定型文テンプレート管理、職員管理など）。
  削除せず、テスト期待値を更新する。
- ただし、view_only に「クラス管理」「定型文テンプレート管理」等が見えることが
  権限設計上妥当かは `routers/settings.py`（該当ルーターの権限ガード）を確認し、
  ガード不足があればproduction側を修正する（本計画ではテスト更新を主としつつ、
  ガード確認をタスクに含める）。

## Task B: `/parent-portal/notices` 一覧の survey 混入修正（優先度: 高・production 修正の可能性あり）

### 現状

`routers/parent_portal.py` の `parent_notice_list()`（2034 行目付近）は
`_load_parent_updates(session, current_parent_user, include_surveys=True)` を
そのまま表示に使っており、**アンケート（survey）がお知らせ一覧に混入する**。

テストの期待（`test_parent_notice_order.py:129`）:

```python
self.assertNotIn('unanswered-survey', self.titles('/parent-portal/notices'))
```

つまり「お知らせ一覧ページには notice のみ表示し、survey はホームにのみ出す」
が元の設計。現在の実装は survey も混在表示する仕様に変わったのか、
フィルタ漏れなのかを確認する必要がある。

### 実装内容

1. `templates/parent_portal/notices.html` と「お知らせ一覧」の画面仕様を確認
   （URL パラメータ `category=survey` は 2048-2054 行目で既にサポートされている）。
2. **デフォルト表示から survey を除外**する（`category` 指定時のみ表示）:

```python
updates = _load_parent_updates(session, current_parent_user, include_surveys=True)
...
if not category:
    # デフォルト（無指定）は notice のみ。survey は category=survey で明示指定時に表示。
    updates = [u for u in updates if u["kind"] != "survey"]
```

   - ※ ただし「混在表示が意図した新仕様」ならテスト側の期待を変更する。
     判断材料: `docs/` 配下の保護者ポータル仕様書、notices.html の
     「お知らせ」という見出し文言、`category=survey` タブの存在。
3. 修正後、`unread_notice_count`（715 行目）や `/parent-portal/attention` への
   影響がないことを確認（attention は `is_unread` フィルタのみで survey を含む
   仕様かどうか）。

### テスト

- `python -m pytest tests/ -q -k "parent_portal" -x` → 既存回帰なし

## Task C: 連絡帳返信の「更新者」表示修正（優先度: 中・production 修正の可能性あり）

### 現状

`test_parent_portal.py::test_staff_can_publish_daily_contact_reply_to_parent`（638 行目）:

```python
self.assertIn("更新者: 台帳担当", staff_detail.text)
```

が失敗。Wave E（P4-3 連絡帳承認フロー）実装時に、連絡帳詳細の
「更新者」表示ロジックが変化し、返信公開後に「更新者」行が
表示されなくなった（または文言が変わった）。

### 実装内容

1. `templates/` 配下の daily contact / 連絡帳詳細テンプレートで
   「更新者」の描画条件を特定する。
2. 原因を分類:
   - **(a) 承認フロー導入で「更新者」→「承認者」等の文言に変わった**場合:
     テスト期待値を実装に合わせて更新する。
   - **(b) 返信公開時に「更新者」行が描画されない regression** の場合:
     テンプレート/ビューの表示条件（例: `if record.updated_by`）を修正し、
     返信公開者を「更新者」として表示する。
3. いずれの場合も「承認済み連絡帳の更新者が承認者を指す」等の
   監査上の意味合いを損なわないこと。

### テスト
